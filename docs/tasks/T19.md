### 最终结果与日志协议

- Setup 默认等待最终事务，不再把 updater handoff 当作安装成功。SetupHelper 记录 request ID，读取 `updates/health/<id>.status.json`，核对 request ID、target version、terminal flag 和 Updater 的实际进程退出码；不用日志字符串判断结果。全局 `updates/update-status.json` 只用于最近状态展示，不能替代对应事务状态。
- 统一枚举 `InstallExitCode`：0 HEALTHY；10 preflight；11 download；12 signature/package/payload verification；13 insufficient space；14 access denied；16 cancelled；21 rolled back；22 rollback failed；23 health failure with rollback；24 unexpected updater termination；25 timeout。NSIS 保留 helper 最终码，语言页与欢迎页取消实测均返回 16。

### 隔离与事务恢复

- 所有故障测试必须设置绝对 `NETBOOT_TEST_ROOT` 和 `.netboot-test-root` 标记。App/SetupHelper/Updater 的安装、用户数据、临时目录、日志、下载、staging、backup、journal 均限制在其子目录；真实 LocalAppData、默认生产安装目录、注册安装目录、越界路径和 reparse 路径 hard fail。

### v1.0.20 更新发现实测与通道决定

- 从 `v1.0.20` tag 导出并构建了原版 `NetBootDhcpTool.Core`，用隔离 RSA 测试密钥签名高版本清单后，实际运行其 `VersionUpdateService.Evaluate`、`UpdatePackageSelector.Select` 和 `DownloadAsync`。当清单只有新 `sevenZipPackages`、旧 `packages` 为空，且顶层归档是 v1.0.20 允许的 `.7z` 名称时：旧解析器忽略未知 `sevenZipPackages`，仍报告 `IsNewVersion=true`，`SelectedPackage=null`；旧 UI 显示“该版本不支持自动升级，下载文件将保存到‘下载’文件夹”，服务只按顶层 SHA 下载，返回 `ReadyToInstall=false`，不会调用旧 Updater。隔离运行日志：`LEGACY_PROBE_SUCCESS version=1.1.0 signed=True packageCount=0 selected=none archive=NetBootDhcpTool-v1.1.0.7z readyToInstall=False bytes=29`。
- 原版解析器拒绝 `.exe` 安装器作为顶层下载 URL（文件名不在其 GitHub/Gitee Release 资产白名单中），所以 v1.0.20 的手动下载 UI 不能分发 Setup.exe。若把 ZIP 留在旧 `packages` 字段，旧 `UpdatePackageSelector` 会选择 Full ZIP 并交给旧 Updater；这是禁止路径。
- 因此采用 Legacy/V2 分流：新安装版本只请求 `latest-v2.json` / `latest-v2.json.sig`，GitHub 与 Gitee 的 V2 清单提供 `sevenZipPackages`；兼容端点 `latest.json` / `.sig` 冻结为经过校验的 v1.0.20 原始内容，继续提供旧 ZIP 链最后版本，不指向新 7z/Setup。v1.0.20 不会发现或下载新包；旧用户从正式 Release 页面下载并运行一次完整安装程序，双语说明配置和数据会保留。Gitee 旧 `/releases/latest` 解析器要求清单版本等于 Release tag，所以冻结清单会被旧客户端排除；新客户端 V2 仍用两个镜像。

### 目标发布模型

完整安装器携带或配套同一份正式 Full 7z 更新 payload。安装器验证 V2 签名清单、Full 7z 文件名/size/SHA-256、包内 `update-package.json` 和 payload 文件清单后，才以事务方式安装。新客户端和 Updater 共用 `IPackageExtractor`、`PackagePathCanonicalizer` 与 ZIP/7z 事务代码；ZIP 保留历史兼容与测试用途，正式网络自动更新默认选择 Full 7z。可选 OTA 7z 不得阻断 Full 回退。两源 Full 7z 的文件名、size、SHA-256 和字节必须一致；源码归档不得进入包候选。Full ZIP 不再是新客户端自动更新的必需资产。

旧版本只在 Release 页面执行这一次完整安装。安装前请求正常关闭旧程序，目标路径经确认并检查权限/空间；备份目标内旧文件，逐项写入已验证 payload，失败时回滚。安装器不得递归删除安装目录，也不得删除或覆盖 `%LOCALAPPDATA%\\NetBootDhcpTool`。经代码确认的配置、网卡/MAC/路由/DHCP 恢复状态、租约、网络历史、操作历史和日志都保存在该 LocalAppData 根目录；Windows 当前网卡配置是系统状态，安装器不得修改。新 App 首次健康检查通过后才提交并切换到 V2 清单。

### 2026-09-29 更新器职责审计与离线 7z PoC

- v1.0.20 源码中，`UpdateController` 在应用进程先调用 `UpdatePackageApplier.ApplyAsync(validateOnly: true)`；Updater 启动后也用同一个方法重新预检，再执行备份、替换、启动健康确认和 rollback。该方法先以 `latest.json.sig` 验证清单，再要求 `request.PackageSha256` 命中签名清单 `packages` 中同 kind 的 SHA，并要求归档 size 与签名 size 一致；随后还校验 ZIP 内 `update-package.json`、目标安装清单和每个 payload 哈希。`update-package.json` 没有独立签名，其信任来自已签名的整包 SHA。该代码与 `v1.0.20` tag 源码相同；本机官方 Updater 二进制 SHA-256 也与官方安装清单一致。
- 7z 与签名 manifest sidecar 校验通过；SharpCompress 0.50.4 隔离解包 54 个文件、122,036,931 字节，与官方解包目录及正式 Full ZIP payload 逐项 SHA-256 一致。一次新鲜 7z 解包耗时 6,224 ms。基于正式 `update-package.json` 和该 staging 生成 Store/NoCompression ZIP 耗时 260 ms、122,052,943 字节；Deflate/Optimal ZIP 耗时 3,970 ms、106,449,583 字节；两者的 54 项 payload size/SHA 都通过。总转换耗时分别为 6,484 ms / 10,194 ms。正式 Full ZIP 是 106,449,589 字节、SHA-256 `f925e90a321c9a946f7d18a65d3ec3283f8099df55e81d0fa5f141cc33d90cde`；Deflate 派生包小 6 字节且 SHA 不同，因此没有满足旧 Updater 的包级签名身份。最终 JSON 证据保存在 `D:\Release\_t19_bridge_validation_20260929\bin\Release\net10.0\validation-run-3\bridge-proof.json`。
- 对 `UpdatePackageApplier.ApplyAsync(validateOnly: true)` 实际运行预检：派生 ZIP 传自身 SHA 时以“package is not listed in the signed manifest”拒绝；传签名 Full ZIP SHA 时以“package SHA-256 does not match”拒绝。官方 Full ZIP 对照组也在 payload 清单匹配处失败：ZIP 元数据路径是 `/`，当前 Windows 校验器将归档路径转为 `\\` 后直接比较，因而报“payload does not match its package manifest”。该路径分隔符缺陷在 `v1.0.20` tag 源码同样存在，必须纳入后续 Updater 修复和回归验证。
- 磁盘估算按实际包计算：payload 122,036,931 B，v1.0.20 的 53 个受管安装文件备份 122,028,359 B；旧 Updater 要求安装卷至少 `payload + backup + 64 MiB = 311,174,154 B`，临时卷至少 `payload + 16 MiB = 138,814,147 B`。本轮 Store 桥接转换同时保留 7z、展开 staging、ZIP 时的峰值为 311,509,307 B（未计临时安全余量），安装阶段还须分别预留 Updater 临时 payload 和备份空间；不同路径落在不同卷时必须按卷分别计算。
- SharpCompress 依赖还没有完成漏洞数据库查询：NuGet 报 NU1900，配置的 `myget.org` 漏洞源索引不可达。这不是已发现漏洞，也不构成 PoC 阻塞；依赖进入产品前必须用可用漏洞库复查 SharpCompress 0.50.4 和传递依赖，查询未成功时保持“未完成”，不得写成“无漏洞”。
- TOCTOU 审计发现校验器先打开并关闭包文件计算 SHA，经过其他检查后再按路径重新打开归档；中间存在替换窗口。随机路径、私有 ACL、`.partial` 原子改名只能降低风险，不能替代 updater 对同一已锁定句柄完成摘要验证和解包。本轮没有把该边界认定为安全通过。
- 结论：当前证据否定“App-side 派生 ZIP + 完全不变的旧 Updater”路线 A；包容器必须命中签名 SHA/size，且旧预检的 Windows 路径比较本身也需修复。按 Plan B 进入 App + Updater 原生 7z 支持，同时保留 ZIP 解析兼容；这轮没有修改 App/Updater 源码，也没有生成可升级的 Bridge OTA 候选，因为尚未实现并验证新的签名 7z 事务输入。现阶段 OTA 大小、Updater 是否能在最终方案保持字节不变、迁移 manifest 的真实签名兼容均未验证。没有创建 tag/Release，没有修改或重发 v1.0.20。

## 实现范围

- 正式发布从 `release.published` 自动同步改为 `workflow_dispatch`。GitHub-hosted 门禁确认标签为稳定格式、位于 `main`，并有同一提交的成功 `windows-ci.yml` push 运行。发布 job 定向到唯一带 `netboot-release` 标签的 Runner，避免恢复时路由到没有对应本地缓存的其他机器。
- GitHub-hosted 门禁还会检查发布标签自身包含发布脚本及依赖文件；过旧标签在派发到自托管 Runner 前明确失败。发布 job 从触发该工作流且通过 CI 的 `main` 提交加载发布工具，同时保留请求标签的应用源码和版本文件；这样可修复发布工具并安全重试旧标签，不移动标签或重建包。
- 发布 job 将固定 .NET SDK 安装到 Runner 用户的 `%LOCALAPPDATA%\NetBootDhcpTool\dotnet`，避免非管理员 Runner 写入 `C:\Program Files\dotnet` 失败，并在同一主机后续发布时复用 SDK。
- 发布脚本把归档和检查点写到 self-hosted Runner 工作目录外的持久缓存；重跑复用原文件，不重新构建。若本地缓存丢失但任一远端 Release 已存在，则失败并要求恢复原缓存，避免重建或产生重复附件。标签、提交或 SHA 不符时安全失败。
- GitHub 与 Gitee Release 仅在不存在时创建；新 GitHub Release 保持 draft、新 Gitee Release 保持 prerelease，直到归档、sidecar 与两端清单都完成读回验证。之后先发布 GitHub，再最后提升 Gitee；重跑可安全完成中断的最后一步。已有资产只有完整下载后哈希匹配才复用；不同内容的同名归档失败关闭，不删除或覆写 Release 资产。
- Gitee 附件上传返回 ID 后立即原子保存 ID 与下载地址。重跑优先通过官方单附件信息/下载 API 按 ID 校验；当前 API 不可用时，用该 ID 对应的已保存下载地址完整读回校验。附件列表只在上传结果不确定或缺失缓存时用于恢复。访问令牌通过 curl 标准输入传递，不写入持久状态目录。Release 元数据使用 JSON 请求；发布清单不得早于两端归档和 sidecar 的完整远端 SHA-256 校验。上传前检查本地文件名与远端附件名相同，避免清单被发布为错误名称。
- 保留 GitHub `main` 与稳定标签到 Gitee 的非强制快进同步。Gitee 上传结果不确定时先恢复附件身份；只有明确未被接受的请求允许有限重试。不跨境下载 GitHub 归档再传 Gitee。
- README、维护指南、待办索引和本发布流程统一指向当前接手入口、唯一状态来源及正式发布步骤；待完成的 Runner/远端验收明确标为阻塞。
