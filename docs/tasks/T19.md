# T19 自托管正式发布与幂等恢复

类型：构建与发布；风险：中。状态见[待办索引](../TODO.md)。用户已授权重构正式发布架构；本任务不发布新的应用版本。

## 目标

保留 GitHub-hosted Windows CI 负责 PR 和日常提交验证。正式 Release 只在精确提交的 Windows CI 通过后，由国内 Windows x64 self-hosted Runner 执行。Runner 对同一标签只构建一次现有 `.7z` 包，并把相同归档和 SHA-256 sidecar 分别上传 GitHub、Gitee。客户端保持现有 `.7z` 格式以及 GitHub/Gitee 实时测速选择。

## 实现范围

- 正式发布从 `release.published` 自动同步改为 `workflow_dispatch`。GitHub-hosted 门禁确认标签为稳定格式、位于 `main`，并有同一提交的成功 `windows-ci.yml` push 运行。发布 job 定向到唯一带 `netboot-release` 标签的 Runner，避免恢复时路由到没有对应本地缓存的其他机器。
- 发布脚本把归档和检查点写到 self-hosted Runner 工作目录外的持久缓存；重跑复用原文件，不重新构建。若本地缓存丢失但任一远端 Release 已存在，则失败并要求恢复原缓存，避免重建或产生重复附件。标签、提交或 SHA 不符时安全失败。
- GitHub 与 Gitee Release 仅在不存在时创建；新 GitHub Release 保持 draft、新 Gitee Release 保持 prerelease，直到归档、sidecar 与两端清单都完成读回验证。之后先发布 GitHub，再最后提升 Gitee；重跑可安全完成中断的最后一步。已有资产只有完整下载后哈希匹配才复用；不同内容的同名归档失败关闭，不删除或覆写 Release 资产。
- Gitee 附件上传返回 ID 后立即原子保存 ID 与下载地址。后续通过官方单附件信息/下载 API 按 ID 校验；附件列表只在上传结果不确定或缺失缓存时用于恢复。访问令牌通过 curl 标准输入传递，不写入持久状态目录。发布清单不得早于两端归档和 sidecar 的完整远端 SHA-256 校验。
- 保留 GitHub `main` 与稳定标签到 Gitee 的非强制快进同步。Gitee 上传只发单次请求；不跨境下载 GitHub 归档再传 Gitee，不使用长时间自动重试循环。
- README、维护指南、待办索引和本发布流程统一指向当前接手入口、唯一状态来源及正式发布步骤；待完成的 Runner/远端验收明确标为阻塞。

## 验收

- [x] 日常 CI 继续使用 GitHub-hosted Windows；正式 publish job 仅使用唯一 self-hosted/windows/x64/netboot-release Runner。
- [x] 正式发布为手动触发，并在运行前核对标签所属提交的精确 CI 成功记录。
- [x] 本地回归验证标签/sidecar/清单一致性、缓存绑定提交、Gitee 附件 ID 持久化、双源清单，以及工作流路由约束。
- [x] 核对 README、维护指南、待办和发布流程的状态与发布入口一致，并更新已过时的 T18/镜像触发说明。
- [ ] 注册唯一 repository-scoped Windows x64 self-hosted Runner，并赋予 `netboot-release` 标签；确认 PowerShell 7、Git、GitHub CLI、curl 7.76+、7-Zip 和持久状态目录可用。
- [ ] 未来正式版本在同一 self-hosted Runner 上验证 GitHub/Gitee 收到完全相同归档；完整下载两端归档和 sidecar 并核对 SHA-256；最后读回两端 `latest.json`。

当前仓库查询到的 self-hosted Runner 数量为 0，因此未触发正式发布工作流，避免将任务排队后误报为已验收。具体发布步骤和恢复方式以[发布流程](../RELEASE_PROCESS.md)为准。
